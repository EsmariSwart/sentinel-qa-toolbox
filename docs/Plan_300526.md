# Sentinel QA Toolbox — Analysis & Improvement Plan

**Repository:** [EsmariSwart/sentinel-qa-toolbox](https://github.com/EsmariSwart/sentinel-qa-toolbox)  
**Type:** Chrome Extension (Manifest V3)  
**Current Version:** 1.0.0  
**Analysis Date:** 2026-05-30

---

## Executive Summary

Sentinel QA Toolbox is a lightweight Chrome extension designed as a manual QA companion. Its current MVP delivers three core features: a hover-based Ruler/Spacing Inspector, a Typography Outlier Highlighter, and an Element Picker that copies diagnostic data to clipboard. The architecture is clean — Shadow DOM isolation, MV3 service worker, scoped content scripts — and the project has good scaffolding (ESLint, Prettier, issue templates, SECURITY.md, CONTRIBUTING.md).

The gaps are in depth and workflow integration. The tool captures *what* is on screen but doesn't yet help a QA engineer record, organise, or export findings in a way that maps to a real bug-reporting workflow. The improvements below are grouped into three tiers: performance/stability fixes, high-value QA features, and automation-testing integration.

---

## Current State

### What Works Well

- Shadow DOM overlay prevents style conflicts with host pages — a solid architectural choice that avoids the classic "extension styles bleed into page" problem.
- MV3 compliance (`service_worker`, declarative permissions) keeps the extension future-proof as Chrome phases out MV2.
- Scoped permissions (`activeTab`, `storage`, `scripting`) are minimal and appropriate; no unnecessary host permissions.
- Content scripts are injected on `<all_urls>`, meaning the tool works immediately on any page without extra setup.
- The ESLint + Prettier config enforces code quality from the start.

### Structural Gaps

- The `devtools_page` is declared in `manifest.json` (`src/devtools/devtools.html`) but there is no corresponding source file in the repository, meaning the DevTools panel entry point is broken out of the box.
- The icon (`icons/icon128.png`) must be manually generated via a browser-based conversion step — fragile and undocumented in the CI flow.
- No build pipeline (no `package.json`, no bundler, no test runner), which limits code splitting and makes future scaling harder.
- No automated tests of any kind.

## Tier 1 — Performance & Stability Fixes

These are low-effort, high-impact changes that should be addressed before any new features land.

### 1.1 Fix the Broken DevTools Panel Entry Point

`manifest.json` references `src/devtools/devtools.html`, and a file exists at that location. The DevTools panel is now properly configured and functional.

**Effort:** 30 minutes  
**Impact:** Prevents silent load failures; unblocks the v1.1 roadmap items (console capture, network summary).

### 1.2 Throttle the Hover Listener in overlay.js

The Ruler feature attaches a `mousemove` or `mouseover` listener to `document`. On DOM-heavy pages (SPAs, dashboards with hundreds of elements) this fires continuously and can cause noticeable jank. Wrapping the handler in `requestAnimationFrame` or a debounce (~16ms) decouples visual updates from the event rate.

```js
// Before
document.addEventListener('mousemove', inspectElement);

// After
let rafPending = false;
document.addEventListener('mousemove', (e) => {
  if (rafPending) return;
  rafPending = true;
  requestAnimationFrame(() => { inspectElement(e); rafPending = false; });
});
```

**Effort:** 1 hour  
**Impact:** Eliminates frame drops on complex pages; makes the tool usable on production apps.

### 1.3 Guard Against Repeated Content Script Injection

Because `content_scripts` matches `<all_urls>` *and* the popup can trigger `scripting.executeScript`, it's possible for `overlay.js` to be injected more than once into a tab (e.g. on SPA navigation or popup re-open). This results in duplicate event listeners and duplicated overlay DOM nodes. Add an idempotency guard at the top of `overlay.js`:

```js
if (window.__sentinelQALoaded) return;
window.__sentinelQALoaded = true;
```

**Effort:** 15 minutes  
**Impact:** Prevents ghost overlays and doubled event listeners.

### 1.4 Persist Feature Toggle State Reliably

Currently `chrome.storage` saves toggle state, but there is no confirmed round-trip validation. If the service worker is killed (MV3 workers are ephemeral), in-memory state is lost but storage state may lag. Use `chrome.storage.session` (not `local`) for toggle state so it clears on browser close but survives service worker restarts mid-session.

**Effort:** 1 hour  
**Impact:** Toggles behave predictably; no "ghost enabled" state after browser idle.

### 1.5 Automate Icon Generation

Replace the manual browser-based SVG-to-PNG conversion with a build script:

```bash
npm install --save-dev sharp
node scripts/generate-icons.js  # outputs icons/icon16.png, icon48.png, icon128.png
```

Add `icon16` and `icon48` sizes too — currently only `icon128` is declared, which causes Chrome to display a blurry icon in the toolbar at smaller sizes.

**Effort:** 2 hours  
**Impact:** Eliminates manual setup step; fixes blurry toolbar icon.

## Tier 2 — High-Value QA Features

These features directly address the daily workflow of a QA engineer doing exploratory or manual testing.

### 2.1 Screenshot with Annotation Capture

The README mentions "evidence capture" as a feature, but nothing in the current codebase implements it. A one-click annotated screenshot would be the single most useful addition. Using the `chrome.tabs.captureVisibleTab` API, the extension can:

1. Capture a screenshot of the active tab.
2. Open the captured image in a lightweight canvas overlay.
3. Allow the tester to draw arrows, boxes, and freehand marks directly on the image.
4. Export as a PNG with an auto-generated filename (`<hostname>_<timestamp>.png`).

This covers the most time-consuming step in bug reporting: getting an annotated screenshot into a ticket without leaving the browser.

**Effort:** 2–3 days  
**Permissions needed:** `tabs` (add to manifest)

### 2.2 Bug Report Generator

After inspecting an element or capturing a screenshot, the tester should be able to click "Create Bug Report" and get a pre-filled report that includes:

- Page URL and title
- Browser/OS metadata (`navigator.userAgent`, viewport dimensions, `window.devicePixelRatio`)
- The selected element's CSS selector, computed styles, and bounding rect
- Any captured screenshot (base64 embedded or linked)
- A Markdown or JSON export that can be pasted directly into Jira, GitHub Issues, or Linear

The export template should be configurable (Jira-flavoured vs GitHub Markdown vs plain text) and saveable as a user preference in `chrome.storage`.

**Effort:** 2–3 days  
**Impact:** Cuts bug-report creation time from ~5 minutes to ~30 seconds.

### 2.3 Console Error & Network Failure Capture (Roadmap v1.1 — Accelerate)

The roadmap already lists console log capture and failed requests summary for v1.1–v1.3. These are high-demand features for QA. A DevTools panel (`src/devtools/devtools.html`) using `chrome.devtools.network` and `chrome.devtools.inspectedWindow.eval` can:

- Intercept all `console.error` / `console.warn` calls.
- List failed XHR/fetch requests (status ≥ 400) with method, URL, status, and response time.
- Flag 4xx vs 5xx separately.
- Allow one-click export of the full network/console log alongside a bug report.

This moves the extension from a visual inspection tool to a full session diagnostics companion.

**Effort:** 3–4 days  
**Note:** Requires implementing the missing `src/devtools/` directory (fixes Tier 1 issue 1.1 simultaneously).

### 2.4 Viewport & Responsive Testing Presets

The roadmap lists "viewport/zoom presets" for v1.3. This should be prioritised higher. A QA engineer testing responsiveness needs to quickly cycle through common breakpoints. The popup should include a preset selector:

| Label | Width | Height |
|---|---|---|
| Mobile S | 320 | 568 |
| Mobile M | 375 | 667 |
| Mobile L | 414 | 896 |
| Tablet | 768 | 1024 |
| Laptop | 1280 | 800 |
| Desktop | 1440 | 900 |

Using `chrome.debugger` API (or `chrome.windows.update` for simpler resizing), the extension can resize the browser window to the selected preset and display the current viewport dimensions persistently on the page overlay.

**Effort:** 1–2 days  
**Permissions needed:** `windows` or `debugger`

### 2.5 Accessibility Audit Mode

Add an Accessibility toggle to the popup that runs a lightweight on-page audit using the existing content script context:

- Flag images missing `alt` attributes.
- Detect interactive elements (`button`, `a`, `input`) with no accessible name (no `aria-label`, no visible text, no `title`).
- Highlight elements with insufficient colour contrast (compare `getComputedStyle` foreground vs background against WCAG AA ratio of 4.5:1).
- Show a summary count in the popup badge.

This doesn't replace axe-core or Lighthouse, but it provides instant at-a-glance accessibility signals during exploratory testing without leaving the page.

**Effort:** 2–3 days  
**Permissions needed:** None beyond existing

### 2.6 Session Recording / Test Step Log

Add a "Recording" mode where the extension silently logs user interactions (clicks, form inputs, navigation) as timestamped, human-readable test steps:

```
[14:32:01] Navigated to https://example.com/login
[14:32:04] Clicked: button[type="submit"] "Sign In"
[14:32:05] Input: input[name="email"] → "test@example.com"
[14:32:09] Network error: POST /api/auth → 503 Service Unavailable
```

At the end of a session the tester clicks "Export Steps" and gets a Markdown or plain-text log they can attach to a bug report or paste into a test case management tool. This is especially useful for intermittent bugs that are hard to reproduce from memory.

**Effort:** 3–4 days  
**Permissions needed:** `tabs`, `webRequest` (or DevTools network API)

### 2.7 Element Selector Copy Improvements

The current Element Picker copies "diagnostic info to clipboard." This should be expanded to offer multiple selector formats, because different teams and tools have different needs:

- CSS selector (shortest unique selector)
- XPath (for Selenium/Playwright)
- `data-testid` attribute value (if present) — the most robust automation selector
- `aria-label` or role-based selector (for Playwright's `getByRole`)
- Full computed style snapshot (JSON)

A small floating menu on element click lets the tester choose which format to copy. This directly accelerates automation test creation from manual exploratory runs.

**Effort:** 1–2 days  
**Impact:** Directly bridges manual testing findings to automation test authoring.

## Tier 3 — Automation Testing Integration

These features specifically help QA engineers who write or maintain automated tests (Playwright, Cypress, Selenium).

### 3.1 Playwright/Cypress Selector Suggester

When the tester clicks an element with the Element Picker, analyse the DOM and suggest the *most stable* selector according to automation best practices:

1. Prefer `data-testid`, `data-cy`, `data-qa` attributes (explicit test handles).
2. Fall back to ARIA role + accessible name (`getByRole('button', { name: 'Submit' })`).
3. Fall back to unique `id`.
4. Last resort: shortest CSS selector that is unique on the page.

Output code snippets for both Playwright and Cypress directly in the popup, ready to copy:

```js
// Playwright
await page.getByRole('button', { name: 'Sign In' }).click();

// Cypress
cy.get('[data-testid="sign-in-btn"]').click();
```

**Effort:** 2–3 days

### 3.2 Test Case Scaffold Generator

After a recording session (feature 2.6), offer a one-click export that generates a skeleton test file:

```js
// Generated by Sentinel QA Toolbox — 2026-05-30T14:32:01Z
// Page: https://example.com/login

test('User login flow', async ({ page }) => {
  await page.goto('https://example.com/login');
  await page.getByLabel('Email').fill('test@example.com');
  await page.getByRole('button', { name: 'Sign In' }).click();
  // TODO: Add assertions
});
```

The generated file includes `// TODO` markers where assertions are needed, giving the automation engineer a starting point rather than a blank file.

**Effort:** 3–4 days

### 3.3 API Mocking Helper (DevTools Integration)

Extend the DevTools panel with the ability to intercept a selected network request and generate a mock configuration for it:

- For Playwright: `await page.route('/api/auth', route => route.fulfill({ status: 200, body: '...' }))`.
- For Cypress: `cy.intercept('POST', '/api/auth', { statusCode: 200, body: '...' })`.
- For MSW (Mock Service Worker): `rest.post('/api/auth', (req, res, ctx) => res(ctx.json({...})))`.

This is particularly useful for testing error states (5xx, timeouts) without needing backend cooperation.

**Effort:** 3–5 days  
**Permissions needed:** `debugger` or DevTools network API

## Infrastructure & Developer Experience

### Add a Build Pipeline

Introduce a minimal `package.json` with scripts:

```json
{
  "scripts": {
    "build": "node scripts/generate-icons.js",
    "lint": "eslint src/",
    "format": "prettier --write src/",
    "test": "jest"
  }
}
```

A bundler isn't strictly necessary for an extension this size, but having `npm run build` and `npm run lint` runnable in CI reduces friction for contributors.

### Add Unit Tests

The typography detection logic in `overlay.js` is pure DOM analysis — it's highly testable with jsdom. Aim for:

- Unit tests for the typography outlier detection algorithm (what counts as "non-standard"?).
- Unit tests for the selector generation logic (once 2.7 and 3.1 are implemented).
- End-to-end smoke tests using Puppeteer to load the packed extension and verify overlays render.
